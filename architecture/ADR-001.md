ADR-001: NIYAM Backend Architecture and First Vertical Slice

Status: Accepted

Date: 2026-08-19

Project: NIYAM

Scope: Backend architecture and first functional vertical slice

Constraint: Approximately 5 days to produce a presentable, functional hackathon backend

1. Context

NIYAM is being developed for the SIH problem statement Human-in-the-Loop Agentic AI for Autonomous Institutional Service Delivery.

The hackathon implementation is intentionally not production-grade. The priority is to demonstrate the problem-solving capability of the statement through a reliable, impressive vertical slice.

The initial target workflow is laboratory booking, while the architecture is designed to support future institutional services such as certificate requests, maintenance tickets, and grievance escalation.

The central principle is:

The AI proposes actions; deterministic backend services validate and execute them.

2. Goals

Separate AI reasoning from institutional execution.

Keep consequential actions behind deterministic backend controls.

Validate incoming requests and AI responses with DTOs.

Use reusable DTO validation for tool arguments.

Persist institutional state in PostgreSQL.

Make the data model multi-tenant-ready while demonstrating one institution.

Make institutional tools extensible without maintaining manual registration code.

Build the vertical slice before adding unnecessary production complexity.

6. DTO Validation

A reusable validator was introduced for tool arguments because tool arguments arrive as Record<string, unknown> and do not automatically pass through controller-level NestJS validation.

export async function validateToolArguments<T extends object>(
  dtoClass: ClassConstructor<T>,
  arguments_: Record<string, unknown>,
): Promise<T> {
  const dto = plainToInstance(dtoClass, arguments_);

  const errors = await validate(dto);

  if (errors.length > 0) {
    throw new BadRequestException(errors);
  }

  return dto;
}

dtoClass is the actual DTO class supplied to the generic function, for example LabBookingArgsDto.

This avoids repetitive field-by-field validation.

7. Institutional Tool Contract

The original interface was changed to an abstract class because TypeScript interfaces disappear at runtime.

Current conceptual contract:

export abstract class InstitutionalTool {
  abstract readonly name: string;

  abstract execute(
    operation: string,
    arguments_: Record<string, unknown>,
    context: ToolExecutionContext,
  ): Promise<unknown>;
}

Concrete tools extend it:

export class LabBookingTool extends InstitutionalTool {
  ...
}

This provides both compile-time enforcement and a runtime-visible base class.

Because LabBookingTool extends the abstract class, its constructor calls super().

8. Tool Execution Context

AI-generated arguments are deliberately separated from trusted backend context.

export interface ToolExecutionContext {
  userId: string;
  requestId: string;
  institutionId: string;
}

AI arguments may contain:

resource
date
start
end
purpose

Trusted context contains:

userId
requestId
institutionId

The AI is not trusted to choose identity or tenant information.

9. Automatic Tool Discovery

Manual registration was rejected because adding every future tool would require changing registration code.

The chosen architecture is:

NestJS DI container
       ↓
DiscoveryService
       ↓
InstitutionalTool providers
       ↓
ToolRegistry

ToolRegistry remains responsible for:

register()

get()

execute()

It should not contain domain-specific knowledge.

Future tools should only need to extend InstitutionalTool and be registered as Nest providers; the registry should discover them automatically.

Duplicate tool names should be rejected.

10. Scheduling Architecture

Scheduling initially used an in-memory array:

private readonly bookings: Booking[] = [];

This was removed after PostgreSQL persistence was introduced.

Current flow:

LabBookingTool
      ↓
SchedulingService
      ↓
PrismaService
      ↓
PostgreSQL

SchedulingService owns:

time-range validation

availability checking

booking creation

booking retrieval

The overlap rule remains:

newStart < existingEnd &&
newEnd > existingStart

Thus 14:00–16:00 and 16:00–18:00 do not conflict, while overlapping intervals do.

18. Security Boundary

The central security principle is:

The AI proposes actions; the deterministic backend authorizes and executes them.

The AI must not control:

user identity
institution identity
database request identity
authorization
database IDs

Those come from backend/application state.

This is central to demonstrating a secure agentic institutional system.

19. RAG Decision

RAG is planned for the FastAPI AI layer for:

verified institutional policies

eligibility rules

booking constraints

policy conflict detection

source-backed answers

A direct PostgreSQL/pgvector approach is considered appropriate for the hackathon.

LangChain is not required by the architecture.

The initial vertical slice may continue using mocked AI reasoning while backend execution is completed.

20. Hackathon Scope Principle

The project is not being optimized for production deployment in five days.

Avoid unnecessary work such as:

complete tenant management

billing

enterprise IAM

separate databases per tenant

distributed event buses

elaborate microservices

full observability stacks

sophisticated policy engines

complete RAG infrastructure before the basic workflow works

The goal is credible architecture plus a working demonstration.

24. Locked Architectural Principles

Unless a later ADR explicitly supersedes them:

AI proposes; backend validates and executes.

Institutional state lives in PostgreSQL.

Tool arguments and trusted execution context remain separate.

Tools remain thin adapters.

Domain logic belongs in domain/application services.

ToolRegistry should not contain domain-specific logic.

Institution is the tenant boundary.

Internal database IDs are not supplied by the AI.

External request identifiers are separate from internal database identity.

Build the first vertical slice before expanding scope.
